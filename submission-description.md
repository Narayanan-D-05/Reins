Reins is a kill switch for AI agent spending: a passkey-rooted spending leash and a settlement-verified counterparty gate, deployed live on Monad Testnet.

**The problem.** AI agents hold long-lived API keys and wallet keys to pay for things autonomously, and unlike a human, an agent doesn't notice when a key leaks, it just keeps calling pay(). GitGuardian found 1,275,105 AI-service secrets exposed on public GitHub in 2025 alone, with 64% of secrets leaked back in 2022 still active today. Meanwhile crypto hacks cost $2.37B in H1 2025 alone (SlowMist), and the "reputation" layer agents are supposed to check before paying a counterparty is cheap to fake: a live empirical study of ERC-8004's reputation extension found 0 valid feedback entries after filtering Sybil activity.

**How it works.** An owner creates one WebAuthn passkey (Face ID, Touch ID, Windows Hello, or a security key). That single passkey does two things in one ceremony: its P256 public key becomes the owner key for a new ReinsAccount smart contract (verified on-chain via Monad's P256/secp256r1 precompile, EIP-7951, address 0x0100), and its WebAuthn PRF extension output, via Mera, deterministically derives the agent's own secp256k1 spending key through standard BIP-44 derivation. No seed phrase, no private key ever stored anywhere, and the agent key is re-derivable on any device from the same passkey.

The owner then signs a spending policy for the agent: a per-payment cap, a daily cap, an expiry, and optional settlement-gate thresholds. Every agent payment calls pay() on-chain, which checks the policy and the settlement gate before anything moves. The settlement gate has two tiers: Tier 1 is a native trust score computed purely from the counterparty's own history of real cleared payments through Reins, publicly recomputable by anyone; Tier 2 is an optional, disclosed external oracle used only for counterparties with no history yet, bounded by a small probation cap so a legitimate new counterparty isn't locked out. No address can rate, vote on, or vouch for another address.

If a key leaks or an agent misbehaves, the owner pulls the reins: one fresh passkey assertion revokes a single agent or every agent under the account, effective from the next block. Every cleared payment also issues a public, re-checkable attestation (via an Attestor contract), so anyone can verify whether an agent's authority was still valid at payment time, not a cached flag.

**What's real.** This is a working app, not a mockup. All five contracts (ReinsAccount, ReceiptBook, Attestor, SettlementGate, ReinsAccountFactory) plus the ERC-8004 Identity Registry are deployed and live on Monad Testnet (chain ID 10143). A full account lifecycle, creation, policy set, and revocation, has been executed end to end with real signed transactions. A public attestation verifier at /app/attestations re-checks live chain state for anyone with no account or API key, and a live cross-account event feed, powered by Envio HyperIndex, streams every policy change, payment, and revocation as it happens.

**Stack.** Monad (P256 precompile), WebAuthn passkeys, Mera (PRF-based deterministic key derivation), ERC-8004 (agent identity), Envio HyperIndex (indexing), Foundry/Solidity (contracts), and a Next.js + viem + wagmi frontend where every owner action signs a real MetaMask transaction.

**What it doesn't claim to solve.** A cold-start counterparty with zero history still looks indistinguishable from fraud at first glance (the probation cap mitigates, doesn't eliminate, this). The optional Tier 2 oracle is a vendor dependency by design, opt-in and swappable, never the sole gate. Revocation stops future spending but can't undo what a compromised key already did under its last valid policy. And recovery after a bad payment clears, reversing rather than just preventing and revealing, is on the roadmap, not in this build.
